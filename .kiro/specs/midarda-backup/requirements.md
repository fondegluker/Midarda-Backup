# Требования к проекту Midarda-Backup

## 1. Обзор

### 1.1. Назначение
Midarda-Backup — система умного резервного копирования файлов бэкапов MSSQL
из локальной папки на удалённые ресурсы (SMB-шара и/или FTP/FTPS),
с контролем целостности, ротацией копий, мониторингом состояния и
уведомлениями.

Проект состоит из двух исполняемых файлов:
- **Установщик** (installer.exe) — консольное приложение с цветным выводом.
- **Служба** (midarda-backup.exe) — Windows-служба, работающая от имени
  пользователя midarda-backup.

### 1.2. Глоссарий
| Термин | Значение |
|--------|----------|
| Мониторинг | Отслеживание появления новых файлов в папке-источнике |
| Транзакция | Полный цикл обработки одного файла (проверка - копирование - ротация) |
| Стабилизация | Ожидание завершения записи файла (закрытие дескриптора + пауза) |
| Ротация | Удаление устаревших копий сверх лимита из конфига |
| Watchdog | Механизм само-мониторинга службы через heartbeat |
| EFS | Encrypting File System — шифрование файлов средствами Windows |

## 2. Функциональные требования — Установщик

### 2.1. Общие
- **У-01.** Консольный установщик на Go, цветной вывод.
- **У-02.** Целевые ОС: Windows Server 2019/2022/2025, только amd64.
- **У-03.** Один .exe установщик + один .exe служба.
- **У-04.** Требует административных привилегий; при отказе UAC — установка прерывается.
- **У-20.** Поддерживает режимы: установка, обновление, удаление.
- **У-21.** При ошибке на этапе мастера конфигурации — установка не откатывается,
  объекты остаются для ручного исправления.

### 2.2. Создание пользователя
- **У-05.** Создаёт пользователя midarda-backup. Если существует — перезаписывает пароль.
- **У-06.** Назначает право «Вход в качестве службы» (SeServiceLogonRight).
- Пароль не проверяется на сложность.

### 2.3. Файлы и шифрование
- **У-07.** Копирует файлы проекта в %ProgramData%\Midarda-Backup, перезаписывая существующие.
- **У-08.** Шифрует конфиг через EFS от имени midarda-backup.
  При недоступности EFS — предупреждение и прерывание установки.
- **У-09.** Записывает пароль пользователя в конфиг перед шифрованием.

### 2.4. Регистрация службы
- **У-10.** Регистрирует службу Midarda-Backup с типом запуска
  Automatic (Delayed) от имени midarda-backup с сохранённым паролем.

### 2.5. Мастер конфигурации
- **У-11.** Запускается как отдельный этап установки.
- **У-12.** Запрашивает путь к папке-источнику (по умолчанию D:\BackUp).
- **У-13.** Запрашивает путь к SMB-шаре (по умолчанию \\FS-01\BackUp).
- **У-14.** Запрашивает путь к FTP (по умолчанию ftp://fs-01:21) с поддержкой FTPS/TLS.
- **У-15.** Если путь не указан — метод не активируется.
- **У-16.** Если не активирован ни один метод — повтор ввода.
- **У-17.** Проверяет доступ: запись и удаление тестового файла от имени
  midarda-backup с введёнными кредами. При ошибке — повтор ввода.
- **У-18.** Запрашивает количество хранимых копий локально и удалённо.
- **У-19.** Запрашивает подсеть для доступа к Health API
  (по умолчанию — локальная подсеть), пользователь может изменить.

### 2.6. Права и запуск
- **У-22.** Устанавливает владельца %ProgramData%\Midarda-Backup = midarda-backup.
- **У-23.** Настраивает ACL: только midarda-backup и SYSTEM. Остальным — запрещено.
- **У-24.** Запускает службу и проверяет её работоспособность.
- **У-25.** Контроль ошибок и информационные сообщения на каждом этапе.
- **У-26.** При обновлении — запрашивает у пользователя, сохранять ли текущий конфиг.
- **У-27.** При удалении — останавливает и удаляет службу, при необходимости
  удаляет пользователя, файлы, конфиг (с подтверждением).

## 3. Функциональные требования — Служба

### 3.1. Общие
- **С-01.** Работает от имени midarda-backup.
- **С-02.** Инициализация из EFS-зашифрованного конфига в %ProgramData%\Midarda-Backup.
- **С-19.** Горячая перезагрузка конфига без перезапуска службы.
- **С-17.** Корректное завершение при Stop/Pause/Resume.

### 3.2. Мониторинг папки
- **С-03.** Мониторинг событийно (ReadDirectoryChangesW).
- **С-36.** Глубина мониторинга — три уровня (корень + 2 вложенных).
- **С-04.** Триггер обработки: закрытие дескриптора файла + стабилизация (пауза из конфига).
- **С-05.** Фильтрация по маске (например, *.bak, *.trn).

### 3.3. Проверка целостности MSSQL
- **С-20.** Переключатель в конфиге: mssql_integrity_check.enabled.
- **С-21.** При включении перед копированием выполняется
  RESTORE VERIFYONLY FROM DISK = '<путь_к_файлу>'.
- **С-22.** Параметры подключения к локальному MSSQL (instance, auth) — в конфиге.
- **С-23.** При нарушении целостности: отмена обработки файла, запись в лог (ERROR),
  email-уведомление.
- **С-24.** Проверка выполняется от имени сервисной учётной записи MSSQL
  или через явные креды из конфига.
- **С-37.** Проверка выполняется до копирования, блокируя.

### 3.4. Копирование на удалённые ресурсы
- **С-06.** Для каждого скопированного файла создаётся контрольная сумма
  в отдельном файле .sha256 рядом с копией.
- **С-07.** Проверка целостности по .sha256 — только для SMB,
  если включено в конфиге (verify_after_copy.smb).
- **С-08.** Для FTP достаточно факта успешной передачи.
- **С-09.** SMB не монтируется; настройки SMB и FTP в конфиге.
- **С-10.** При недоступности удалённого ресурса — запись в лог
  и продолжение работы со вторым ресурсом.
- **С-38.** Реакция на несовпадение .sha256: retry/лог, количество попыток
  из конфига (по умолчанию 1).

### 3.5. Ротация копий
- **С-11.** Учитываются все файлы в подпапке (включая .sha256).
- **С-12.** Удаляются все лишние файлы сверх лимита.
- **С-13.** Сортировка по дате изменения файла.

### 3.6. Защита от зависания
- **С-29.** Таймауты для операций SMB/FTP/MSSQL — в конфиге.
- **С-30.** Детекция зависания операции: отсутствие прогресса > N секунд.
- **С-31.** При зависании операции: прервать, записать в лог, отправить email.
- **С-32.** Watchdog для службы: само-мониторинг через heartbeat (отдельный thread).
  При отсутствии heartbeat — перезапуск службы и email-уведомление.

### 3.7. Retry
- **С-33.** Exponential backoff для retry.
- **С-34.** Количество попыток из конфига, по умолчанию 1.
- **С-35.** Комбинировать с таймаутами из С-29.

### 3.8. Логирование
- **С-14.** Формат: текст.
- **С-15.** Уровни: DEBUG/INFO/WARN/ERROR.
- **С-16.** Ротация: по размеру 5 МБ, количество файлов — 5.
- **С-39.** Лог-файл в папке приложения.

### 3.9. Health API и Metrics
- **С-40.** Доступ только для подсети из конфига.
- **С-41.** Endpoint /health: расширенный JSON с деталями по каждому ресурсу
  (SMB, FTP, MSSQL), количеством локальных и удалённых копий,
  датой последней удачной транзакции.
- **С-42.** Endpoint /metrics для Prometheus и Zabbix.
- **С-43.** Порт по умолчанию: 91873.

### 3.10. Уведомления на email
- **С-25.** Настройки SMTP в конфиге: host, port, auth, from, to, tls.
- **С-26.** Если уведомления включены — отправляются все алерты, ошибки и предупреждения.
- **С-27.** При зависании транзакции — email-уведомление.
- **С-28.** При перезапуске службы — email-уведомление.

## 4. Нефункциональные требования

- **Н-01.** Локализация: только русский (сообщения, документация).
- **Н-02.** Логи установщика — только консоль.
- **Н-03.** Тестирование: unit + интеграционные тесты.
- **Н-04.** Документация: README, инструкция администратора, схема развёртывания.
- **Н-05.** Распространение без ограничений.
- **Н-06.** Формат конфига: TOML (поддержка комментариев, строгая типизация,
  библиотека BurntSushi/toml).
- **Н-07.** В документации явно прописать, чем чревата смена пароля
  пользователя midarda-backup после установки:
  - EFS-сертификат привязан к профилю пользователя; смена пароля сама по себе
    EFS не ломает, но сброс пароля администратором (без знания старого) делает
    профиль недоступным и конфиг нерасшифровываемым.
  - Пароль службы в SCM также нужно обновлять вручную.
  - Рекомендуется менять пароль только через net user с указанием старого пароля,
    либо переустанавливать службу.

## 5. Ограничения и допущения

- Только Windows Server 2019/2022/2025, amd64.
- MSSQL — локальный на той же машине.
- Мониторинг — три уровня вложенности папок.
- Внешние Go-библиотеки разрешены.
