# Requirements Document

## Introduction

Midarda-Backup — система резервного копирования файлов резервных копий Microsoft SQL Server из локального каталога в удалённые назначения SMB и FTP/FTPS. Система обнаруживает завершённые файлы, при необходимости проверяет резервные копии средствами MSSQL, создаёт контрольные суммы SHA-256, независимо доставляет файлы в настроенные назначения, выполняет ротацию, публикует состояние и метрики и отправляет уведомления.

Поставка предназначена только для Windows Server 2019, 2022 и 2025 на архитектуре amd64 и содержит два исполняемых файла: консольный установщик `installer.exe` и Windows-службу `midarda-backup.exe`.

Настоящий документ является авторитетным источником требований. Существующие `design.md` и `tasks.md` должны быть приведены в соответствие с настоящим документом на следующих фазах workflow.

## Glossary

- **Midarda-Backup**: вся поставляемая система, включающая Установщик и Службу.
- **Установщик**: консольное приложение `installer.exe`, которое устанавливает, обновляет и удаляет Службу.
- **Служба**: Windows-служба `midarda-backup.exe`, которая обрабатывает Файлы_резервных_копий.
- **Администратор**: пользователь Windows с административными полномочиями, запускающий Установщик.
- **Сервисная_учётная_запись**: локальная учётная запись Windows `midarda-backup`, от имени которой работает Служба.
- **SCM**: Windows Service Control Manager, регистрирующий, запускающий и восстанавливающий Службу.
- **Каталог_приложения**: каталог `%ProgramData%\Midarda-Backup`.
- **Конфигурация**: EFS-зашифрованный файл `config.toml` в Каталоге_приложения.
- **Мастер_конфигурации**: интерактивный этап Установщика, формирующий Конфигурацию.
- **Каталог_источника**: один настроенный локальный каталог с Файлами_резервных_копий.
- **Файл_резервной_копии**: обычный файл в Каталоге_источника, соответствующий хотя бы одной Маске_файлов и не имеющий суффикса `.sha256`.
- **Маска_файлов**: регистронезависимый шаблон Windows для выбора имён Файлов_резервных_копий, например `*.bak` или `*.trn`.
- **Допустимая_глубина**: расположение файла в корне Каталога_источника или в подкаталоге первого либо второго уровня; числовые значения глубины равны 0, 1 и 2.
- **Событие_файла**: событие создания, переименования в целевое имя, изменения размера или времени последней записи, полученное через `ReadDirectoryChangesW`.
- **Стабилизация**: подтверждение готовности файла после успешного открытия без совместного доступа на запись и удаление и неизменности пары «размер, время изменения» в течение настроенного Интервала_стабилизации.
- **Идентичность_файла**: совокупность канонического пути, идентификатора файла Windows, размера и времени изменения.
- **Транзакция**: полный цикл обработки одной Идентичности_файла от проверки MSSQL до копирования, ротации и обновления состояния.
- **Назначение**: включённый удалённый ресурс SMB_назначение или FTP_назначение.
- **SMB_назначение**: удалённый UNC-каталог SMB, доступный без подключения сетевого диска.
- **FTP_назначение**: удалённый ресурс FTP либо explicit FTPS.
- **Sidecar**: текстовый файл `<имя_файла>.sha256`, содержащий SHA-256 Файла_резервной_копии.
- **Публикация**: завершённая запись Файла_резервной_копии и соответствующего Sidecar в Назначение.
- **MSSQL_проверка**: блокирующее выполнение `RESTORE VERIFYONLY` для Файла_резервной_копии на локальном экземпляре MSSQL.
- **Ротация**: детерминированное удаление файлов сверх настроенного лимита в непосредственно затронутом каталоге.
- **Попытка**: одно ограниченное таймаутами выполнение операции MSSQL, SMB или FTP.
- **Повтор**: новая Попытка после временной ошибки.
- **Таймаут_операции**: максимальная продолжительность одной Попытки.
- **Таймаут_прогресса**: максимальный допустимый интервал без увеличения числа обработанных байтов или сигнала активности операции.
- **Heartbeat**: периодически обновляемая временная отметка активности основного цикла Службы.
- **Watchdog**: независимый механизм контроля возраста Heartbeat.
- **Горячая_перезагрузка**: атомарная замена действующего снимка Конфигурации без перезапуска Службы.
- **Снимок_конфигурации**: неизменяемая версия полностью разобранной и проверенной Конфигурации.
- **Health_API**: HTTP-интерфейс состояния с endpoint `/health`.
- **Metrics_API**: HTTP-интерфейс метрик Prometheus с endpoint `/metrics`, пригодный для чтения HTTP-agent системы Zabbix.
- **Разрешённая_подсеть**: единственный CIDR-префикс IPv4 или IPv6, из которого разрешены запросы Health_API и Metrics_API.
- **EFS**: Windows Encrypting File System, используемая для шифрования всего файла Конфигурации.
- **ACL**: список управления доступом Windows к Каталогу_приложения и дочерним объектам.
- **Оповещение**: типизированное событие уровня WARN, ERROR или alert, предназначенное для SMTP-уведомления.
- **Полный_успех**: результат Транзакции, при котором MSSQL_проверка успешно завершена либо выключена и каждое включённое Назначение успешно опубликовано и проверено согласно настройкам.
- **Частичный_успех**: результат Транзакции, при котором хотя бы одно включённое Назначение успешно обработано, а хотя бы одно включённое Назначение завершилось ошибкой.
- **Инструкция_администратора**: русскоязычный эксплуатационный документ для установки, настройки, обновления, удаления и сопровождения Midarda-Backup.
- **Квалификация_релиза**: набор проверок поставки на поддерживаемых версиях Windows Server перед выпуском релиза.
- **MSSQL_gate**: блокирующее решение MSSQL_проверки, разрешающее создание Sidecar и последующие этапы Транзакции только после успешной проверки либо при выключенной проверке.
- **Интервал_стабилизации**: настроенная продолжительность неизменности пары «размер, время изменения», необходимая для завершения Стабилизации.
- **Marker_Watchdog**: сохраняемая отметка причины завершения процесса по решению Watchdog.
- **Нормализованная_Конфигурация**: Конфигурация после применения значений по умолчанию и успешной проверки межполевых ограничений.
- **Эквивалентная_Конфигурация**: Нормализованная_Конфигурация, значения всех типизированных полей которой совпадают со значениями сравниваемой Нормализованной_Конфигурации независимо от порядка TOML-ключей и комментариев.
- **Нормализованный_путь**: стабильное представление канонического Windows-пути для детерминированного сравнения, при котором один канонический путь при каждом преобразовании получает одно и то же значение.
- **Basename**: последний компонент пути с именем файла без компонентов родительских каталогов.
- **Payload**: последовательность байтов содержимого файла.
- **Verifier**: компонент Службы, выполняющий MSSQL_проверку и возвращающий классифицированный результат.
- **Retry_policy**: правила ограничения Попыток, прекращения Повторов и вычисления задержек между Попытками.
- **Progress_event**: увеличение числа обработанных байтов или сигнал активности операции, от которого заново отсчитывается Таймаут_прогресса.
- **Root_cancellation**: отмена корневого контекста выполнения Службы.
- **Candidate_reload**: полностью разобранная кандидатная Конфигурация, предлагаемая для замены действующего Снимка_конфигурации.
- **Runtime_snapshot**: снимок текущего состояния Службы, используемый для формирования публичного ответа Health_API.
- **Lifecycle**: текущее состояние запуска, работы, паузы или остановки Службы.
- **Логический_вызов_Назначения**: обработка одной ветви Назначения в рамках Транзакции, включающая все Попытки и Повторы этой ветви.
- **EFS_lifecycle**: формирование, EFS-шифрование и проверка Конфигурации согласно Requirement 4.

## Requirements

### Requirement 1: Состав поставки и поддерживаемая платформа

**User Story:** Как администратор, я хочу получить однозначный комплект поставки для поддерживаемых серверов, чтобы устанавливать систему без дополнительных runtime-компонентов проекта.

#### Acceptance Criteria

1. **У-01.** THE Установщик SHALL предоставлять русскоязычный консольный интерфейс с цветовым различением сообщений INFO, WARN и ERROR.
2. **У-02.** WHEN Установщик запускается на Windows Server 2019, 2022 или 2025 с архитектурой amd64, THE Установщик SHALL разрешать выбранную операцию жизненного цикла.
3. **У-03.** THE Midarda-Backup SHALL поставляться в виде двух исполняемых файлов `installer.exe` и `midarda-backup.exe` для `windows/amd64`.
4. **Н-01.** THE Midarda-Backup SHALL предоставлять сообщения оператора на русском языке.
5. **Н-01.** THE Midarda-Backup SHALL предоставлять эксплуатационную документацию на русском языке.
6. **Н-02.** THE Установщик SHALL выводить журнал установки только в консоль.
7. **Н-05.** THE Midarda-Backup SHALL включать условия распространения, не вводящие ограничений на копирование и использование поставки.
8. IF Установщик запускается на неподдерживаемой версии Windows или неподдерживаемой архитектуре, THEN THE Установщик SHALL завершать операцию до изменения системы с сообщением ERROR.

### Requirement 2: Режимы Установщика и административные полномочия

**User Story:** Как администратор, я хочу выбирать установку, обновление или удаление и получать предсказуемую обработку полномочий, чтобы безопасно управлять жизненным циклом Службы.

#### Acceptance Criteria

1. **У-20.** THE Установщик SHALL предоставлять режимы установки, обновления и удаления.
2. **У-04.** WHEN выбранный режим требует изменения Windows, THE Установщик SHALL проверить наличие административных полномочий до изменения Windows.
3. **У-04.** IF выбранный режим требует изменения Windows и процесс не имеет повышенного token, THEN THE Установщик SHALL один раз запросить повышение через UAC.
4. IF Администратор отклоняет запрос UAC, THEN THE Установщик SHALL завершать операцию до изменения системы с ненулевым кодом завершения.
5. **У-25.** WHEN Установщик начинает этап операции, THE Установщик SHALL вывести русскоязычное сообщение INFO с названием этапа.
6. **У-25.** WHEN Установщик успешно завершает этап операции, THE Установщик SHALL вывести русскоязычное сообщение INFO с названием этапа.
7. **У-25.** IF этап операции завершается ошибкой, THEN THE Установщик SHALL вывести русскоязычное сообщение ERROR с названием этапа.
8. IF этап до запуска Мастера_конфигурации завершается ошибкой, THEN THE Установщик SHALL прекратить последующие этапы и сохранить возможность повторного идемпотентного запуска.
9. **У-21.** IF Мастер_конфигурации завершается ошибкой, THEN THE Установщик SHALL прекратить установку без удаления уже созданных учётной записи, каталогов и файлов.

### Requirement 3: Сервисная учётная запись

**User Story:** Как администратор, я хочу запускать Службу под выделенной учётной записью, чтобы изолировать полномочия резервного копирования.

#### Acceptance Criteria

1. **У-05.** WHEN режим установки обнаруживает отсутствие Сервисной_учётной_записи, THE Установщик SHALL создать Сервисную_учётную_запись с введённым паролем.
2. **У-05.** WHEN режим установки обнаруживает существующую Сервисную_учётную_запись, THE Установщик SHALL установить для Сервисной_учётной_записи введённый пароль.
3. WHEN системные API управления локальными учётными записями Windows принимают введённый пароль, THE Установщик SHALL использовать введённый пароль без применения отдельного правила сложности Midarda-Backup.
4. IF системные API управления локальными учётными записями Windows отклоняют введённый пароль, THEN THE Установщик SHALL сообщить об отклонении пароля без применения отдельного правила сложности Midarda-Backup.
5. **У-06.** WHEN Сервисная_учётная_запись создана или найдена, THE Установщик SHALL назначить Сервисной_учётной_записи право `SeServiceLogonRight`.
6. **С-01.** WHILE Служба выполняет рабочий цикл, THE Служба SHALL работать в контексте Сервисной_учётной_записи.

### Requirement 4: Файлы, EFS и ACL

**User Story:** Как администратор, я хочу защитить файлы приложения и секреты Конфигурации средствами Windows, чтобы доступ имели только Служба и SYSTEM.

#### Acceptance Criteria

1. **У-07.** WHEN выполняется установка или обновление, THE Установщик SHALL атомарно копировать поставляемые файлы в Каталог_приложения с заменой существующих версий.
2. **У-09.** WHEN Установщик формирует Конфигурацию, THE Установщик SHALL записать пароль Сервисной_учётной_записи в поле `service_account.password` до EFS-шифрования.
3. **У-08.** WHEN Конфигурация сформирована, THE Установщик SHALL зашифровать весь файл Конфигурации посредством EFS в загруженном профиле Сервисной_учётной_записи.
4. **У-08.** WHEN EFS-шифрование завершено, THE Установщик SHALL проверить атрибут шифрования Конфигурации.
5. **У-08.** WHEN EFS-шифрование завершено, THE Установщик SHALL проверить чтение Конфигурации в контексте Сервисной_учётной_записи.
6. IF том Каталога_приложения не поддерживает EFS или проверка EFS завершается ошибкой, THEN THE Установщик SHALL удалить незашифрованный временный файл.
7. IF том Каталога_приложения не поддерживает EFS или проверка EFS завершается ошибкой, THEN THE Установщик SHALL вывести ERROR.
8. IF том Каталога_приложения не поддерживает EFS или проверка EFS завершается ошибкой, THEN THE Установщик SHALL прекратить установку.
9. **У-22.** WHEN Каталог_приложения создан или обновлён, THE Установщик SHALL назначить Сервисную_учётную_запись владельцем Каталога_приложения.
10. **У-23.** WHEN Установщик защищает Каталог_приложения, THE Установщик SHALL отключить наследование ACL.
11. **У-23.** WHEN наследование ACL Каталога_приложения отключено, THE Установщик SHALL предоставить полный доступ к Каталогу_приложения только Сервисной_учётной_записи и `SYSTEM`.
12. **С-02.** WHEN Служба запускается, THE Служба SHALL прочитать Конфигурацию из Каталога_приложения через прозрачное расшифрование EFS в контексте Сервисной_учётной_записи.

### Requirement 5: Регистрация и жизненный цикл Windows-службы

**User Story:** Как администратор, я хочу зарегистрировать управляемую Windows-службу с автоматическим восстановлением, чтобы резервное копирование работало после перезагрузок и сбоев.

#### Acceptance Criteria

1. **У-10.** WHEN установка завершила подготовку защищённых файлов, THE Установщик SHALL зарегистрировать Службу `Midarda-Backup` в SCM под Сервисной_учётной_записью с типом запуска Automatic (Delayed Start).
2. WHEN Установщик регистрирует Службу, THE Установщик SHALL передать SCM введённый пароль Сервисной_учётной_записи.
3. WHEN Установщик регистрирует Службу, THE Установщик SHALL настроить перезапуск после ненулевого завершения процесса.
4. **У-24.** WHEN регистрация и настройка Службы завершены, THE Установщик SHALL запустить Службу.
5. **У-24.** WHEN Установщик запускает Службу во время установки, THE Установщик SHALL дождаться состояния Running в пределах настроенного таймаута.
6. **У-24.** WHEN Служба достигает состояния Running во время установки, THE Установщик SHALL получить успешный локальный ответ Health_API.
7. **С-17.** WHEN SCM передаёт команду Pause, THE Служба SHALL прекратить запуск новых Транзакций.
8. **С-17.** WHEN SCM передаёт команду Pause, THE Служба SHALL разрешить текущей Транзакции завершиться.
9. **С-17.** WHILE Служба находится в состоянии Pause, THE Служба SHALL продолжать работу Health_API, Metrics_API и Watchdog.
10. **С-17.** WHEN SCM передаёт команду Continue, THE Служба SHALL возобновить запуск новых Транзакций.
11. **С-17.** WHEN SCM передаёт команду Stop или Shutdown, THE Служба SHALL прекратить приём новой работы.
12. **С-17.** WHEN SCM передаёт команду Stop или Shutdown, THE Служба SHALL отменить выполняющиеся операции.
13. **С-17.** WHEN SCM передаёт команду Stop или Shutdown, THE Служба SHALL ожидать завершения отменяемых операций не дольше `shutdown_timeout`.
14. **С-17.** WHEN ожидание отменяемых операций завершено или достигнут `shutdown_timeout`, THE Служба SHALL сбросить буферы журнала.
15. **С-17.** WHEN буферы журнала сброшены после команды Stop или Shutdown, THE Служба SHALL сообщить SCM состояние Stopped.

### Requirement 6: Мастер конфигурации и проверка доступа

**User Story:** Как администратор, я хочу интерактивно задать источник, назначения и эксплуатационные параметры, чтобы получить проверенную Конфигурацию до запуска Службы.

#### Acceptance Criteria

1. **У-11.** WHEN этапы подготовки учётной записи и файлов завершены, THE Установщик SHALL запустить Мастер_конфигурации как отдельный этап установки.
2. **У-12.** WHEN Мастер_конфигурации запрашивает Каталог_источника, THE Мастер_конфигурации SHALL предложить `D:\BackUp` как значение по умолчанию.
3. **У-13.** WHEN Мастер_конфигурации запрашивает SMB_назначение, THE Мастер_конфигурации SHALL предложить `\\FS-01\BackUp` как значение по умолчанию.
4. **У-14.** WHEN Мастер_конфигурации запрашивает FTP_назначение, THE Мастер_конфигурации SHALL предложить `ftp://fs-01:21` как значение по умолчанию.
5. **У-14.** WHEN Мастер_конфигурации запрашивает FTP_назначение, THE Мастер_конфигурации SHALL запросить режим plain FTP либо explicit FTPS.
6. **У-15.** WHEN Администратор подтверждает пустое значение пути Назначения, THE Мастер_конфигурации SHALL записать соответствующее Назначение как выключенное.
7. **У-16.** IF SMB_назначение и FTP_назначение выключены, THEN THE Мастер_конфигурации SHALL повторить ввод назначений.
8. **У-17.** WHEN введён Каталог_источника, THE Установщик SHALL проверить создание, чтение и удаление случайного тестового файла в Каталоге_источника в контексте Сервисной_учётной_записи.
9. **У-17.** WHEN введено включённое Назначение, THE Установщик SHALL проверить создание, чтение и удаление случайного тестового файла в Назначении с применением настроенных credentials Назначения в контексте Сервисной_учётной_записи.
10. IF проверка доступа к Каталогу_источника или включённому Назначению завершается ошибкой, THEN THE Мастер_конфигурации SHALL показать категорию ошибки без раскрытия credentials, полного содержимого строки подключения или иных секретов.
11. IF проверка доступа к Каталогу_источника или включённому Назначению завершается ошибкой, THEN THE Мастер_конфигурации SHALL повторить ввод параметров ресурса, проверка которого завершилась ошибкой.
12. **У-18.** WHEN Мастер_конфигурации запрашивает ротацию, THE Мастер_конфигурации SHALL принять целые значения `local_keep` и `remote_keep`, не меньшие нуля.
13. **У-19.** WHEN Мастер_конфигурации запрашивает Разрешённую_подсеть, THE Мастер_конфигурации SHALL предложить CIDR активного IP-интерфейса с наименьшей метрикой маршрута как значение по умолчанию.
14. IF автоматическое определение Разрешённой_подсети не находит активный IP-интерфейс, THEN THE Мастер_конфигурации SHALL предложить `127.0.0.1/32` как значение по умолчанию.
15. WHEN MSSQL_проверка включена, THE Установщик SHALL проверить подключение к локальному MSSQL до сохранения Конфигурации только после успешного прохождения проверок доступа к Каталогу_источника и включённым Назначениям согласно У-17.
16. WHEN MSSQL_проверка включена, THE Установщик SHALL проверить доступ MSSQL к тестовому Файлу_резервной_копии до сохранения Конфигурации только после успешного прохождения проверок доступа к Каталогу_источника и включённым Назначениям согласно У-17.

### Requirement 7: Строгая TOML-конфигурация и горячая перезагрузка

**User Story:** Как администратор, я хочу использовать строго проверяемую TOML-конфигурацию с атомарным обновлением, чтобы изменения не приводили к частично применённому состоянию.

#### Acceptance Criteria

1. **Н-06.** THE Конфигурация SHALL использовать формат TOML, совместимый с `BurntSushi/toml`.
2. **Н-06.** THE Конфигурация SHALL поддерживать комментарии TOML.
3. **Н-06.** THE Служба SHALL строго сопоставлять Конфигурацию с типизированной моделью.
4. WHEN Конфигурация не содержит необязательное поле, THE Служба SHALL применить документированное значение по умолчанию до проверки межполевых ограничений.
5. IF Конфигурация содержит синтаксическую ошибку, неизвестный ключ, неверный тип или нарушение межполевого ограничения, THEN THE Служба SHALL отклонить всю Конфигурацию с диагностикой без раскрытия секретов.
6. WHEN Служба принимает допустимую Конфигурацию, THE Служба SHALL создать неизменяемый Снимок_конфигурации с монотонно возрастающей версией.
7. **С-19.** WHEN файл Конфигурации атомарно заменён допустимой новой версией, THE Служба SHALL подготовить затронутые ресурсы до применения нового Снимка_конфигурации.
8. **С-19.** WHEN подготовка затронутых ресурсов для допустимой новой версии завершена успешно, THE Служба SHALL атомарно применить новый Снимок_конфигурации без перезапуска процесса.
9. IF новая Конфигурация недопустима или подготовка нового watcher либо HTTP listener завершается ошибкой, THEN THE Служба SHALL сохранить предыдущий Снимок_конфигурации.
10. IF новая Конфигурация недопустима или подготовка нового watcher либо HTTP listener завершается ошибкой, THEN THE Служба SHALL записать WARN.
11. IF новая Конфигурация недопустима или подготовка нового watcher либо HTTP listener завершается ошибкой, THEN THE Служба SHALL увеличить счётчик ошибок reload.
12. IF новая Конфигурация недопустима или подготовка нового watcher либо HTTP listener завершается ошибкой, THEN THE Служба SHALL сформировать Оповещение.
13. WHILE Транзакция выполняется, THE Служба SHALL использовать один Снимок_конфигурации, захваченный в начале Транзакции.
14. IF новая Конфигурация изменяет `service_account.username`, THEN THE Служба SHALL отклонить новую Конфигурацию с требованием переустановки.
15. THE Служба SHALL исключать пароли, tokens и строки подключений из журналов.
16. THE Health_API SHALL исключать пароли, tokens и строки подключений из ответов.
17. THE Metrics_API SHALL исключать пароли, tokens и строки подключений из метрик.
18. THE Конфигурация SHALL принимать порт Health_API только в диапазоне от 1 до 65535 включительно.
19. THE Конфигурация SHALL принимать `max_attempts` только со значением не меньше 1, причём значение 1 означает одну Попытку без Повтора.
20. THE Конфигурация SHALL принимать Таймаут_прогресса только как положительную длительность, не превышающую соответствующий Таймаут_операции.

### Requirement 8: Обнаружение и стабилизация файлов

**User Story:** Как администратор, я хочу обрабатывать только завершённые резервные копии из допустимой части дерева, чтобы исключить копирование незаконченных и посторонних файлов.

#### Acceptance Criteria

1. **С-03.** WHILE Служба работает, THE Служба SHALL получать События_файла посредством `ReadDirectoryChangesW` с наблюдением поддерева Каталога_источника.
2. **С-36.** WHEN Служба классифицирует путь События_файла, THE Служба SHALL принимать только пути Допустимой_глубины.
3. **С-05.** WHEN Служба классифицирует обычный файл Допустимой_глубины, THE Служба SHALL принимать файл только при регистронезависимом соответствии basename хотя бы одной Маске_файлов.
4. IF канонический путь находится вне Каталога_источника, имеет глубину больше 2, обозначает каталог или имеет регистронезависимый суффикс `.sha256`, THEN THE Служба SHALL исключить путь из очереди Транзакций.
5. **С-04.** WHEN принятый путь успешно открывается без совместного доступа на запись и удаление и пара «размер, время изменения» остаётся неизменной в течение Интервала_стабилизации, THE Служба SHALL объявить Идентичность_файла готовой к Транзакции.
6. WHEN пара «размер, время изменения» изменяется во время Стабилизации, THE Служба SHALL перезапустить Интервал_стабилизации без запуска Транзакции.
7. IF файл не удаётся открыть без совместного доступа на запись и удаление во время Стабилизации, THEN THE Служба SHALL перезапустить Интервал_стабилизации без запуска Транзакции.
8. WHEN несколько Событий_файла относятся к одной ожидающей Идентичности_файла, THE Служба SHALL объединить события в одну ожидающую запись и перезапустить Стабилизацию.
9. WHEN Событие_файла изменяет выполняемую Идентичность_файла, THE Служба SHALL пометить путь для повторной Стабилизации после текущей Транзакции.
10. IF буфер `ReadDirectoryChangesW` переполняется или ограниченная очередь заполнена, THEN THE Служба SHALL запланировать повторное сканирование Каталога_источника на Допустимой_глубине после освобождения очереди.

### Requirement 9: Блокирующая проверка MSSQL

**User Story:** Как администратор, я хочу блокировать доставку резервной копии, которую MSSQL не подтвердил, чтобы не распространять заведомо непроверенные файлы.

#### Acceptance Criteria

1. **С-20.** WHERE `mssql_integrity_check.enabled=true`, THE Служба SHALL выполнять MSSQL_проверку каждой готовой Идентичности_файла.
2. **С-21.** WHEN Служба выполняет MSSQL_проверку, THE Служба SHALL выполнить `RESTORE VERIFYONLY FROM DISK = N'<канонический_путь>'` для абсолютного пути внутри Каталога_источника с безопасным экранированием одинарных кавычек.
3. **С-22.** THE Конфигурация SHALL определять локальный MSSQL instance и режим аутентификации `windows` либо `sql`.
4. **С-24.** WHERE выбран режим `windows`, THE Служба SHALL подключаться к MSSQL в контексте Windows identity Службы.
5. **С-24.** WHERE выбран режим `sql`, THE Служба SHALL подключаться к MSSQL с username и password из Конфигурации.
6. **С-37.** WHILE MSSQL_проверка не завершилась успешно, THE Служба SHALL удерживать создание Sidecar, Публикацию и Ротацию для соответствующей Идентичности_файла.
7. **С-23.** IF MSSQL_проверка возвращает ошибку целостности, доступа, подключения или таймаута после исчерпания допустимых Попыток, THEN THE Служба SHALL завершить Транзакцию со статусом failed.
8. **С-23.** IF MSSQL_проверка возвращает ошибку целостности, доступа, подключения или таймаута после исчерпания допустимых Попыток, THEN THE Служба SHALL записать ERROR.
9. **С-23.** IF MSSQL_проверка возвращает ошибку целостности, доступа, подключения или таймаута после исчерпания допустимых Попыток, THEN THE Служба SHALL сформировать Оповещение.
10. WHERE MSSQL_проверка выключена, THE Служба SHALL перейти к созданию Sidecar без вызова Verifier.
11. WHEN MSSQL_проверка завершается успешно, THE Служба SHALL перейти к созданию Sidecar.

### Requirement 10: SHA-256 и формат Sidecar

**User Story:** Как администратор, я хочу получать однозначную контрольную сумму рядом с каждой копией, чтобы проверять соответствие содержимого.

#### Acceptance Criteria

1. **С-06.** WHEN MSSQL_gate разрешает обработку, THE Служба SHALL потоково вычислить SHA-256 Файла_резервной_копии.
2. **С-06.** WHEN потоковое вычисление SHA-256 завершено успешно, THE Служба SHALL атомарно создать локальный Sidecar.
3. THE Служба SHALL записывать Sidecar в формате `<64 строчных шестнадцатеричных символа><два пробела><basename>\n`.
4. WHEN Служба публикует Файл_резервной_копии в Назначение, THE Служба SHALL публиковать соответствующий Sidecar рядом с удалённой копией.
5. WHEN допустимый Sidecar разбирается и повторно форматируется, THE Служба SHALL воспроизвести тот же digest и basename.

### Requirement 11: Независимая доставка в SMB и FTP/FTPS

**User Story:** Как администратор, я хочу независимо использовать SMB и FTP/FTPS, чтобы отказ одного назначения не блокировал другое.

#### Acceptance Criteria

1. **С-09.** WHERE SMB_назначение включено, THE Служба SHALL обращаться к абсолютному UNC-пути непосредственно без подключения сетевого диска.
2. WHERE FTP_назначение включено с `tls=false`, THE Служба SHALL использовать plain FTP в пассивном бинарном режиме.
3. WHERE FTP_назначение включено с `tls=true`, THE Служба SHALL использовать explicit FTPS с проверкой цепочки доверия и hostname сертификата.
4. WHEN Служба публикует файл в Назначение, THE Служба SHALL сохранить относительную структуру каталогов Каталога_источника.
5. WHEN Назначение поддерживает атомарное переименование, THE Служба SHALL записать backup и Sidecar под уникальными активными временными именами с префиксом `.partial-`.
6. WHEN Назначение поддерживает атомарное переименование и запись временного объекта завершена успешно, THE Служба SHALL переименовать соответствующий временный объект в итоговое имя.
7. WHERE FTP_назначение не поддерживает переименование, WHEN финальный ответ каждой операции `STOR` подтверждает успех, THE Служба SHALL считать непосредственно записанный итоговый объект опубликованным.
8. **С-07.** WHERE `smb.verify_after_copy=true`, WHEN SMB-публикация backup и Sidecar завершена, THE Служба SHALL повторно прочитать опубликованный backup и сравнить SHA-256 с локальным значением.
9. **С-08.** WHEN FTP или FTPS возвращает успешный финальный протокольный ответ для backup и Sidecar, THE Служба SHALL считать FTP-публикацию успешной без обратного чтения SHA-256.
10. **С-10.** IF одно включённое Назначение недоступно или завершается ошибкой, THEN THE Служба SHALL записать ошибку соответствующей ветви и попытаться обработать каждое другое включённое Назначение.
11. **С-38.** IF обратная SMB-проверка обнаруживает несовпадение SHA-256, THEN THE Служба SHALL классифицировать ошибку как временную `checksum_mismatch`.
12. **С-38.** IF обратная SMB-проверка обнаруживает несовпадение SHA-256, THEN THE Служба SHALL сделать повреждённую публикацию недоступной как успешную Публикацию посредством удаления либо изоляции.
13. **С-38.** IF обратная SMB-проверка обнаруживает несовпадение SHA-256, THEN THE Служба SHALL применить настроенную политику Повторов.
14. WHEN все включённые Назначения завершаются успешно, THE Служба SHALL присвоить Транзакции статус succeeded.
15. WHEN часть включённых Назначений завершается успешно и часть завершается ошибкой, THE Служба SHALL присвоить Транзакции статус partial.
16. WHEN каждое включённое Назначение завершается ошибкой, THE Служба SHALL присвоить Транзакции статус failed.
17. WHEN SMB_назначение и FTP_назначение отключены (ни одно Назначение не включено), THEN THE Служба SHALL присвоить Транзакции статус failed.

### Requirement 12: Ротация локальных и удалённых копий

**User Story:** Как администратор, я хочу применять детерминированные лимиты хранения к каждому затронутому каталогу, чтобы ограничивать объём хранимых файлов.

#### Acceptance Criteria

1. **С-11.** WHEN Служба строит план Ротации каталога, THE Служба SHALL учитывать все обычные файлы непосредственного каталога, включая Sidecar и файлы неизвестных расширений.
2. **С-11.** WHEN Служба строит план Ротации каталога, THE Служба SHALL исключать каталоги и активные файлы `.partial-*`.
3. **С-13.** WHEN Служба упорядочивает учитываемые файлы, THE Служба SHALL сортировать файлы по времени изменения по убыванию и по Нормализованному_пути по возрастанию при равном времени.
4. **С-12.** WHEN число учитываемых файлов превышает лимит `keep`, THE Служба SHALL удалить каждый файл после первых `keep` элементов упорядоченного списка.
5. WHEN лимит `keep` равен нулю, THE Служба SHALL включить все учитываемые файлы в план удаления.
6. WHEN Назначение успешно опубликовало backup и Sidecar, THE Служба SHALL выполнить удалённую Ротацию в соответствующем непосредственно затронутом подкаталоге с лимитом `remote_keep`.
7. IF получение списка удалённого каталога завершается ошибкой, THEN THE Служба SHALL пропустить удаления в соответствующем каталоге.
8. IF получение списка удалённого каталога завершается ошибкой, THEN THE Служба SHALL записать ERROR.
9. IF получение списка удалённого каталога завершается ошибкой, THEN THE Служба SHALL сформировать Оповещение.
10. IF удаление отдельного файла завершается ошибкой, THEN THE Служба SHALL продолжить остальные удаления.
11. IF удаление отдельного файла завершается ошибкой, THEN THE Служба SHALL включить ошибку в результат Ротации.
12. WHEN ветви включённых Назначений завершены, THE Служба SHALL выполнить локальную Ротацию соответствующего подкаталога Каталога_источника с лимитом `local_keep`.
13. WHEN Ротация повторно применяется к уже приведённому к лимиту неизменённому каталогу, THE Служба SHALL сформировать пустой план удаления.

### Requirement 13: Таймауты, прогресс и Повторы

**User Story:** Как администратор, я хочу ограничить зависшие операции и число повторов, чтобы Служба сохраняла предсказуемое время реакции.

#### Acceptance Criteria

1. **С-29.** THE Конфигурация SHALL задавать отдельные Таймауты_операции для SMB, FTP и MSSQL.
2. **С-30.** IF возраст последнего увеличения обработанных байтов или сигнала активности строго превышает Таймаут_прогресса, THEN THE Служба SHALL отменить текущую Попытку как `stalled`.
3. WHEN число обработанных байтов увеличивается или операция подаёт сигнал активности, THE Служба SHALL отсчитывать Таймаут_прогресса от времени нового события прогресса.
4. **С-31.** IF операция остаётся `stalled` после исчерпания допустимых Попыток, THEN THE Служба SHALL записать ERROR.
5. **С-31.** IF операция остаётся `stalled` после исчерпания допустимых Попыток, THEN THE Служба SHALL сформировать Оповещение.
6. **С-33.** WHEN временная ошибка допускает следующую Попытку, THE Служба SHALL выдержать задержку `min(max_interval, initial_interval × multiplier^(i-1))`, где `i` является номером завершившейся Попытки начиная с 1.
7. **С-34.** THE Служба SHALL ограничивать общее число Попыток значением `max_attempts`, включая первую Попытку.
8. **С-35.** WHEN Служба запускает Попытку, THE Служба SHALL назначить Попытке отдельный Таймаут_операции и Таймаут_прогресса.
9. IF Попытка завершается успехом, постоянной ошибкой или отменой корневого контекста, THEN THE Служба SHALL прекратить Повторы соответствующей операции.
10. IF Попытка завершается временной сетевой ошибкой, временной SQL-ошибкой, timeout, `stalled` или `checksum_mismatch`, THEN THE Служба SHALL выполнить Повтор при наличии неиспользованной Попытки.
11. IF Попытка завершается ошибкой validation, authentication, TLS certificate, path escape или MSSQL integrity, THEN THE Служба SHALL классифицировать ошибку как постоянную.
12. IF результат Попытки соответствует одновременно временной и постоянной категориям ошибок, THEN THE Служба SHALL применить постоянную категорию.

### Requirement 14: Watchdog и восстановление после зависания

**User Story:** Как администратор, я хочу автоматически восстанавливать зависшую Службу, чтобы основной цикл возвращался в работу без ручного вмешательства.

#### Acceptance Criteria

1. **С-32.** WHEN Служба извлекает Транзакцию из очереди, THE Служба SHALL обновить Heartbeat.
2. **С-32.** WHEN Служба завершает этап Транзакции, THE Служба SHALL обновить Heartbeat.
3. **С-32.** WHILE Служба работает без извлечения Транзакции и завершения этапа Транзакции, THE Служба SHALL обновлять Heartbeat на настроенном idle-интервале.
4. **С-32.** WHILE Служба работает, THE Watchdog SHALL независимо контролировать возраст Heartbeat.
5. IF возраст Heartbeat строго превышает `watchdog.timeout`, THEN THE Watchdog SHALL один раз записать Marker_Watchdog причины.
6. IF возраст Heartbeat строго превышает `watchdog.timeout`, THEN THE Watchdog SHALL попытаться записать ERROR в пределах отдельного таймаута.
7. IF возраст Heartbeat строго превышает `watchdog.timeout`, THEN THE Watchdog SHALL попытаться отправить Оповещение в пределах отдельного таймаута.
8. WHEN Watchdog завершает попытки записать ERROR и отправить Оповещение после превышения `watchdog.timeout`, THE Watchdog SHALL завершить процесс с ненулевым кодом.
9. WHEN SCM обнаруживает ненулевое завершение Службы, THE SCM SHALL перезапустить Службу согласно настроенной recovery policy.
10. **С-28.** WHEN Служба запускается и обнаруживает Marker_Watchdog, THE Служба SHALL сформировать Оповещение о перезапуске.
11. **С-28.** WHEN Оповещение о перезапуске после обнаружения Marker_Watchdog поставлено в очередь, THE Служба SHALL удалить Marker_Watchdog.
12. THE Конфигурация SHALL принимать `watchdog.timeout` только со значением больше `watchdog.heartbeat_interval`.

### Requirement 15: Текстовое логирование

### Requirement 16: Health API и Metrics API

**User Story:** Как оператор, я хочу получать защищённое состояние и метрики Службы, чтобы интегрировать Midarda-Backup с мониторингом.

#### Acceptance Criteria

1. **С-43.** THE Health_API SHALL использовать порт `91873` по умолчанию.
2. **С-40.** WHEN запрос к `/health` или `/metrics` поступает с socket IP-адреса внутри Разрешённой_подсети, THE Служба SHALL разрешить обработку запроса.
3. **С-40.** IF socket IP-адрес запроса находится вне Разрешённой_подсети, THEN THE Служба SHALL вернуть HTTP 403 без раскрытия состояния.
4. IF socket remote address имеет неверный формат, THEN THE Служба SHALL вернуть HTTP 400.
5. WHEN Служба принимает решение о доступе, THE Служба SHALL игнорировать заголовок `X-Forwarded-For`.
6. **С-41.** WHEN разрешённый клиент выполняет `GET /health`, THE Health_API SHALL вернуть JSON UTF-8 со статусом Службы, версией Конфигурации, состояниями SMB, FTP и MSSQL, количеством локальных и удалённых копий, временем последней успешной Транзакции и возрастом Heartbeat.
7. WHEN состояние Службы равно `healthy` или `degraded`, THE Health_API SHALL вернуть HTTP 200 для `GET /health`.
8. WHEN состояние Службы равно `unhealthy`, THE Health_API SHALL вернуть HTTP 503 для `GET /health`.
9. **С-42.** WHEN разрешённый клиент выполняет `GET /metrics`, THE Metrics_API SHALL вернуть метрики в текстовом формате Prometheus, доступном HTTP-agent системы Zabbix.
10. THE Metrics_API SHALL публиковать счётчики Транзакций, результатов операций Назначений, Повторов, скопированных байтов, reload и Оповещений, а также длительности операций, возраст Heartbeat и количество копий.
11. WHEN запрос к `/health` или `/metrics` использует метод, отличный от GET, THE Служба SHALL вернуть HTTP 405.
12. WHILE Lifecycle работает, Конфигурация допустима, Heartbeat не просрочен и последнее состояние каждого включённого ресурса успешно, THE Health_API SHALL классифицировать Службу как `healthy`.
13. WHILE основной цикл и Heartbeat работают, WHEN происходит частичный сбой Назначения, reload, Ротации или notifier, THE Health_API SHALL классифицировать Службу как `degraded`.
14. IF Heartbeat просрочен, startup завершился ошибкой или Служба не способна обрабатывать Файлы_резервных_копий, THEN THE Health_API SHALL классифицировать Службу как `unhealthy`.
15. THE Health_API SHALL исключать credentials, полные пути, сырые ошибки и stack traces из ответов.
16. THE Metrics_API SHALL исключать полные пути, имена файлов, сырые ошибки и секреты из значений labels.

### Requirement 17: SMTP-уведомления

### Requirement 18: Обновление и удаление

**User Story:** Как администратор, я хочу обновлять и удалять систему с явным выбором судьбы конфигурации и учётной записи, чтобы не потерять EFS-данные случайно.

#### Acceptance Criteria

1. **У-26.** WHEN выбран режим обновления, THE Установщик SHALL запросить решение о сохранении существующей Конфигурации.
2. WHEN Администратор выбирает сохранение Конфигурации, THE Установщик SHALL проверить расшифрование существующей Конфигурации.
3. WHEN Администратор выбирает сохранение Конфигурации, THE Установщик SHALL проверить валидность существующей Конфигурации.
4. WHEN расшифрование и проверка валидности сохраняемой Конфигурации завершены успешно, THE Установщик SHALL заменить остальные поставляемые файлы без перезаписи Конфигурации.
5. WHEN Администратор выбирает замену Конфигурации, THE Установщик SHALL выполнить Мастер_конфигурации.
6. WHEN Мастер_конфигурации для заменяемой Конфигурации завершён успешно, THE Установщик SHALL выполнить EFS_lifecycle заново.
7. WHEN обновление заменило файлы, THE Установщик SHALL повторно применить ACL.
8. WHEN обновление заменило файлы, THE Установщик SHALL повторно применить SCM policy.
9. WHEN ACL и SCM policy повторно применены после обновления, THE Установщик SHALL запустить Службу.
10. WHEN Служба запущена после обновления, THE Установщик SHALL проверить Health_API.
11. **У-27.** WHEN выбран режим удаления, THE Установщик SHALL остановить Службу до удаления Конфигурации, файлов или Сервисной_учётной_записи.
12. **У-27.** WHEN Служба остановлена в режиме удаления, THE Установщик SHALL удалить Службу до удаления Конфигурации, файлов или Сервисной_учётной_записи.
13. **У-27.** WHEN Служба удалена, THE Установщик SHALL отдельно запросить подтверждение удаления Конфигурации и файлов.
14. **У-27.** WHEN Служба удалена, THE Установщик SHALL отдельно запросить подтверждение удаления Сервисной_учётной_записи.
15. WHEN подтверждено удаление Сервисной_учётной_записи, THE Установщик SHALL удалить Сервисную_учётную_запись после обработки решения об удалении Конфигурации и файлов.
16. IF Администратор сохраняет EFS-зашифрованную Конфигурацию и удаляет Сервисную_учётную_запись, THEN THE Установщик SHALL вывести предупреждение о вероятной утрате доступа к EFS-ключу.

### Requirement 26: Свойство P-07 — Детерминированная Ротация

### Requirement 31: Свойство P-12 — Полный fan-out Оповещений

**User Story:** Как сопровождающий разработчик, я хочу проверять маршрутизацию произвольных последовательностей событий, чтобы подтвердить полный fan-out SMTP-оповещений.

#### Acceptance Criteria

1. WHERE SMTP-уведомления включены, WHEN произвольная последовательность типизированных событий обрабатывается, THE Служба SHALL поставить в SMTP-очередь каждый WARN, ERROR и alert ровно один раз.
2. WHERE SMTP-уведомления включены, WHEN произвольная последовательность типизированных событий обрабатывается, THE Служба SHALL исключить каждый DEBUG и INFO из SMTP-очереди.
3. WHERE SMTP-уведомления выключены, THE Служба SHALL сохранять SMTP-очередь пустой для любой последовательности событий.

**Связанные критерии:** С-26.

### Requirement 32: Свойство P-13 — CIDR как единственный источник решения о доступе

**User Story:** Как сопровождающий разработчик, я хочу проверять решение о HTTP-доступе для произвольных адресов и заголовков, чтобы подтвердить применение только socket IP и Разрешённой_подсети.

#### Acceptance Criteria

1. WHEN произвольный корректно разобранный socket IP и набор HTTP headers проверяются для `/health` или `/metrics`, THE Служба SHALL разрешить запрос тогда и только тогда, когда socket IP принадлежит Разрешённой_подсети, независимо от значения `X-Forwarded-For`.

**Связанные критерии:** С-40.

### Requirement 33: Свойство P-14 — Безопасный round trip Health JSON

**User Story:** Как сопровождающий разработчик, я хочу проверять round trip публичного Health JSON, чтобы сохранить состояние и исключить раскрытие секретов.

#### Acceptance Criteria

1. WHEN произвольный Runtime_snapshot сериализуется в Health JSON и разбирается повторно, THE Health_API SHALL сохранить публичные status, timestamp, config version, состояния ресурсов, copy counts и Heartbeat.
2. THE Health_API SHALL исключать каждый секрет Конфигурации и каждую сырую ошибку из сериализованного Health JSON.

**Связанные критерии:** С-41.

### Requirement 34: Ограничения и допущения

**User Story:** Как сопровождающий разработчик, я хочу зафиксировать границы и допущения проекта, чтобы реализация соответствовала согласованной области Midarda-Backup.

#### Acceptance Criteria

1. THE Midarda-Backup SHALL поддерживать развёртывание, в котором MSSQL расположен на той же машине, что и Служба.
2. THE Midarda-Backup SHALL поддерживать один Каталог_источника, не более одного SMB_назначения и не более одного FTP_назначения при наличии минимум одного включённого Назначения.
3. THE Midarda-Backup SHALL ограничивать область проекта резервным копированием без GUI, создания плановых backup jobs MSSQL, восстановления баз данных, облачных хранилищ, дедупликации и распределённой координации.
4. IF одно Назначение завершается сбоем и Служба получает новое Событие_файла для соответствующего пути, THEN THE Служба SHALL автоматически включить повторную попытку для ранее сбойного Назначения в новой Транзакции.
5. THE Midarda-Backup SHALL допускать использование внешних Go-библиотек в реализации.

### Requirement 35: Уточнения устранённых противоречий

**User Story:** Как сопровождающий разработчик, я хочу сохранить однозначные решения по устранённым противоречиям, чтобы следующие фазы спецификации применяли те же значения и определения.

#### Acceptance Criteria

1. THE Health_API SHALL использовать значение порта `91873` по умолчанию.
2. THE Служба SHALL определять «закрытие дескриптора» через проверяемую Стабилизацию.
3. THE Служба SHALL определять «три уровня» как корень и два вложенных уровня с числовой глубиной 0–2.
4. THE Конфигурация SHALL определять `max_attempts` как общее число Попыток, включая первую.
5. WHEN каждое включённое Назначение завершается успешно, THE Служба SHALL считать Транзакцию успешно завершённой.
6. WHEN результаты включённых Назначений содержат успех и ошибку, THE Служба SHALL присвоить Транзакции статус partial, который не является Полным_успехом.
7. IF Watchdog обнаруживает зависший процесс, THEN THE Watchdog SHALL завершить процесс с Marker_Watchdog для последующего восстановления средствами SCM.
8. WHEN Watchdog завершает зависший процесс с ненулевым кодом, THE SCM SHALL выполнять перезапуск согласно настроенной recovery policy.
9. THE Ротация SHALL учитывать каждый обычный файл, включая Sidecar, как отдельную запись.
10. THE Ротация SHALL применять лимиты к числу файлов, а не к числу пар backup/Sidecar.

**Обоснование критерия 2:** `ReadDirectoryChangesW` не предоставляет отдельного надёжного события закрытия файла.
